Talaia

Un panell autoallotjat per gestionar una flota de VPS Debian: cada contenidor per separat quan només vols tocar una app, o el servidor sencer quan cal anar a fons. Combina el millor de Portainer, Komodo, Coolify, Dockge i Cockpit en una sola eina.

AutoallotjatLlicència WNCL-TP-1.0Agent lleuger en GoSense ports oberts als VPSSense dependència: res deixa de funcionar si el treus

Una talaia és la torre de guaita de la costa: des d'un sol punt veus tot el litoral i avises si alguna cosa no va bé. És exactament el que ha de fer el panell. A més, és curt, es pronuncia bé en qualsevol idioma i el domini i el binari queden nets: talaia, talaia-agent, talaiactl.

Com encaixa tot

Arquitectura

Un nucli central i un agent a cada VPS. Els agents són els que obren la connexió cap al nucli, així els VPS no necessiten cap port obert. El nucli no executa res directament als servidors: envia ordres als agents i aquests les executen i en tornen el resultat.

Peces del sistema

Components

talaia-core

Nucli

Binari únic en Go. Es desplega amb un compose.yaml (nucli + Postgres) en un VPS petit o a casa.

  • API REST + WebSocket per al panell
  • Servidor gRPC per als agents
  • Cua de tasques persistent (River, sobre Postgres)
  • Emissió de certificats per als agents (CA interna)
  • Serveix el panell web ja compilat
talaia-agent

Agent

Binari de ~15 MB, paquet .deb i servei systemd. Consum objectiu: <30 MB de RAM i <1% de CPU en repòs.

  • Mòduls: docker, compose, systemd, journal, apt, metrics, files, firewall, cron, users, pty, backup, proxy
  • Memòria local de mètriques (24 h) per si cau la connexió
  • Reconnexió automàtica amb espera progressiva
talaia-web

Panell

React + TypeScript. Tema clar i fosc, paleta d'ordres (⌘K) i funciona bé al mòbil per a consultes ràpides.

  • Terminal web (xterm.js)
  • Editor de compose i fitxers (Monaco)
  • Gràfics lleugers (uPlot)
  • Logs i estat en temps real
talaiactl

CLI

Tot el que fa el panell, des del terminal o des d'un pipeline de CI.

  • talaiactl deploy botiga
  • talaiactl exec vps-web-01 -- df -h
  • talaiactl sync ./infra (GitOps)
Proxy

Dominis i SSL

Caddy a cada servidor, gestionat per l'agent via la seva API d'administració. HTTPS automàtic amb Let's Encrypt.

  • Assignar domini a un contenidor en un clic
  • Redireccions, autenticació bàsica, capçaleres
Plantilles

Catàleg d'apps

Repositori de plantilles Compose amb variables: Postgres, MariaDB, Redis, n8n, Nextcloud, Gitea, Vaultwarden, Uptime Kuma, WordPress…

  • Catàlegs propis afegint un repo Git
El requisit clau

Gestionar un contenidor o el servidor sencer

Talaia té dos nivells de treball sobre el mateix model. Pots entrar a un sol contenidor o stack sense veure res més, o obrir el servidor i gestionar-ho tot. Els permisos segueixen la mateixa jerarquia: pots donar accés només a una app (a un client, per exemple) sense que pugui tocar el servidor.

Mode contenidor

Una app, aïllada

  • Stacks Compose i contenidors solts
  • Editar compose i variables, amb historial de versions
  • Logs, estadístiques, terminal dins el contenidor
  • Desplegar, reiniciar, revertir a la versió anterior
  • Domini i SSL, còpies de volums, webhooks
  • Adoptar contenidors existents creats fora de Talaia
Mode servidor

La màquina sencera

  • Mètriques del sistema, discos, xarxa
  • Serveis systemd i logs de journald
  • Paquets apt i actualitzacions de seguretat, avís de reinici necessari
  • Tallafoc (nftables/ufw), fail2ban, ports oberts
  • Usuaris, claus SSH, cron i timers
  • Explorador de fitxers, terminal de l'amfitrió, auditoria d'enduriment
Organització→Grup (prod, clients…)→Servidor→Stack / App→Contenidor

Un permís donat en un nivell s'hereta cap avall. Lector a «prod» veu tots els servidors de producció. Operador a l'stack «botiga» pot veure logs, reiniciar i desplegar aquella app i res més.

Sense dependència: els stacks es guarden a /opt/talaia/stacks/<nom>/compose.yaml, igual que a Dockge. Si desinstal·les Talaia, tot continua funcionant i ho pots gestionar amb docker compose com sempre.

Com s'uneix un VPS

Connexió i seguretat

Afegir un servidor és una sola ordre. A partir d'aquí, tota la comunicació va xifrada amb certificats mútues i cada ordre queda registrada.

  1. Generes un testimoni al panell«Afegir servidor» crea un testimoni d'un sol ús que caduca en 15 minuts.
  2. Executes l'instal·lador al VPSAfegeix el repositori apt signat, instal·la talaia-agent i activa el servei systemd.
  3. L'agent genera la seva clauCrea una clau privada que no surt mai del servidor i envia una sol·licitud de certificat amb el testimoni.
  4. El nucli signa el certificatLa CA interna emet un certificat de 90 dies lligat a l'ID del servidor. Es renova sol.
  5. Connexió permanentL'agent obre un túnel gRPC sobre mTLS cap al port 443 del nucli. Heartbeat cada 10 s, mètriques cada 15 s.
  6. Inventari inicialL'agent envia SO, maquinari, contenidors, projectes Compose i serveis. El servidor apareix a la flota.
# Pas 2: al VPS, com a root
curl -fsSL https://talaia.exemple.cat/install.sh \
  | bash -s -- --token tl_enr_8fK2…q9

# o bé, manualment
apt install talaia-agent
talaia-agent enroll --url https://talaia.exemple.cat \
  --token tl_enr_8fK2…q9
// proto/agent.proto (resum)
service AgentHub {
  rpc Connect(stream AgentMsg) returns (stream CoreMsg);
}
message CoreMsg {             // nucli → agent
  string job_id = 1;          // idempotent
  oneof cmd { ComposeUp up = 2; ExecPty pty = 3;
              AptUpgrade apt = 4; ReadLogs logs = 5; … }
}
message AgentMsg {            // agent → nucli
  oneof msg { Heartbeat hb = 1; Metrics m = 2;
              JobEvent ev = 3; Inventory inv = 4; … }
}
Xarxa

Els VPS no obren cap port per a Talaia. El nucli només necessita el 443. Opcionalment, el panell pot quedar visible només dins de WireGuard o Tailscale.

Privilegis

L'agent necessita root (accedir al socket de Docker ja ho equival). Per limitar el risc, cada mòdul es pot desactivar a /etc/talaia/agent.toml, i el nucli mai pot executar res que no sigui una ordre tipada o una terminal explícita.

Si cau el nucli

Els contenidors i serveis continuen funcionant. L'agent guarda mètriques i esdeveniments 24 h i els envia en reconnectar.

Secrets

Les variables secretes es xifren amb age al nucli i només es desxifren a l'agent destí en el moment del deploy. Mai apareixen als logs.

Accés

Contrasenya + 2FA obligatori, passkeys, límit d'intents, sessions revocables, i cada acció a l'auditoria amb usuari, IP i resultat.

Cadena de subministrament

Binaris reproduïbles, paquets i imatges signats (cosign), i l'agent verifica la signatura abans d'auto-actualitzar-se.

Fase 0 · setmanes 1–2

Fonaments

Preparar el terreny perquè després tot vagi ràpid.

  • Monorepo, CI amb proves i lint
  • Contracte proto/ v0 i generació de codi
  • Esquelet del nucli amb Postgres i migracions
  • Esquelet del panell, tokens de disseny, tema clar/fosc
  • Dos VPS de prova amb Debian 12 i 13

Llest quan: make dev aixeca nucli + panell + un agent buit en local.

Fase 1 · setmanes 3–6

Agent, connexió i inventari

El cor del sistema. Si això és sòlid, la resta és afegir mòduls.

  • Alta amb testimoni, CA interna, mTLS
  • Túnel gRPC amb reconnexió i heartbeat
  • Inventari: SO, maquinari, contenidors, serveis
  • Mètriques en directe
  • Pantalla de Flota (maqueta 1)
  • Paquet .deb i install.sh

Llest quan: els teus VPS reals apareixen a la flota amb mètriques, i sobreviuen a un reinici del nucli.

Fase 2 · setmanes 7–11

Contenidors i stacks

El substitut de Portainer i Dockge.

  • Contenidors: accions, logs, estadístiques, terminal
  • Stacks Compose a /opt/talaia/stacks
  • Editor de compose i .env
  • Adoptar projectes existents
  • Imatges, volums, xarxes, neteja
  • Pantalla d'stack (maqueta 3)

Llest quan: pots deixar d'usar Portainer per a tot el que fas ara.

Fase 3 · setmanes 12–16

Servidor sencer

El substitut de Cockpit, multi-servidor.

  • systemd: estat, arrencar/aturar, habilitar
  • journald amb filtres i cerca
  • apt: pendents, seguretat, actualitzar, reinici necessari
  • Terminal de l'amfitrió
  • Usuari únic amb 2FA i auditoria
  • Pantalla de servidor (maqueta 2)

Llest quan: passes una setmana sense entrar per SSH als VPS.

Fita MVP · ~4 mesos. Talaia ja és la teva eina diària. A partir d'aquí, cada fase afegeix potència.
Fase 4 · setmanes 17–19

Usuaris, permisos i auditoria

Obrir l'eina a altres persones amb seguretat.

  • Usuaris, equips, rols i abasts
  • Passkeys i OIDC
  • Gravació de sessions de terminal
  • Claus d'API; primera versió de talaiactl
  • Pantalla de permisos (maqueta 5)

Llest quan: un usuari amb accés a un sol stack no pot veure ni tocar res més, verificat amb proves automàtiques.

Fase 5 · setmanes 20–22

Monitoratge i alertes

Que Talaia t'avisi abans que t'avisin els usuaris.

  • Historial en TimescaleDB amb agregació
  • Regles d'alerta i silenciament
  • Comprovacions HTTP/TCP i certificats
  • Telegram, ntfy, correu, Discord, webhook

Llest quan: si s'atura un contenidor o un disc passa del 90%, reps l'avís en menys d'un minut.

Fase 6 · setmanes 23–28

Deploys, dominis i plantilles

La part de Coolify.

  • Stacks des de Git i webhooks
  • Build amb Dockerfile i Nixpacks
  • Deploy sense aturada i revertir
  • Caddy gestionat: dominis + SSL
  • Catàleg de plantilles (15 apps inicials)
  • Assistent de nova app (maqueta 4)

Llest quan: fer push a main publica l'app amb HTTPS sense tocar res més.

Fase 7 · setmanes 29–31

Còpies de seguretat

La funció que no vols necessitar però que ha de funcionar.

  • Plans amb restic per volums i carpetes
  • Bolcats de bases de dades coherents
  • Destins S3, B2, SFTP
  • Restaurar des del panell

Llest quan: has restaurat una base de dades real en un servidor nou des del panell.

Fase 8 · setmanes 32–35

Flota i automatització

La part de Komodo i Ansible.

  • Accions en bloc per grup
  • Procediments programats
  • Tallafoc, usuaris SSH, cron, fitxers
  • Auditoria d'enduriment
  • Sincronització GitOps (TOML)

Llest quan: pots recrear tota la configuració de Talaia des d'un repo Git.

Fase 9 · setmanes 36–38

Versió 1.0

Polir, documentar i publicar.

  • Revisió de seguretat i proves de càrrega (50 agents)
  • Auto-actualització signada de l'agent
  • Documentació i guia d'instal·lació
  • Suport arm64, paquets signats

Llest quan: algú altre l'instal·la seguint només la documentació.

Abans de començar

Riscos i decisions obertes

Risc · abast

Voler-ho tot alhora

És el risc més gran. Defensa: no començar una fase fins que l'anterior compleix el criteri de «llest», i apuntar idees noves en una llista per a després.

Risc · seguretat

Una clau per a tots els servidors

Si algú entra al panell, entra a tot. Defensa: 2FA obligatori, panell darrere de VPN, auditoria i la possibilitat de desactivar mòduls perillosos per servidor.

Risc · manteniment

Plantilles i versions de Docker

El catàleg envelleix ràpid. Defensa: poques plantilles ben provades i catàlegs externs per a la resta.

Decisió oberta

Postgres o SQLite

Proposta: Postgres. SQLite simplificaria la instal·lació per a una sola persona, però les mètriques i la cua van millor amb Postgres. Es pot revisar a la fase 0.

Decisió oberta

React o SvelteKit

Proposta: React, per l'ecosistema. Si ja domines Svelte, és igual de vàlid i més lleuger.

Decisió presa

Llicència

WNCL-TP-1.0: ús i còpia lliures, prohibit lucrar-se'n i autoria de CatLinux sempre visible.
